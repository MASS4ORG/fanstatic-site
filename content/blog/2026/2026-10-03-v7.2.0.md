A broken Liquid template used to cost you an afternoon: one error per rendered page, no file, no line, and a build that still reported success. Fanstatic v7.2.0 fixes that, and closes two more bugs that were quietly corrupting your `public/` folder and your build report.

## Template errors with file and line

Every template error is now reported once, with the exact location and the source line that caused it:

```
[ERR] 'themes/my-theme/_default/baseof.html:34:5': template not found: 'partials/baseof-footer.html' (rendering 'blog/2025/2025-01-30-v6.1.0.md')
  {% render 'partials/baseof-footer.html' %}
```

Syntax errors caught during theme compilation look the same:

```
[ERR] 'themes/my-theme/_default/single.html:12:3': 'unknown_tag' is not a known tag
  {% unknown_tag %}
```

Templates are compiled before rendering starts, so a typo in your theme is reported immediately instead of once per page. Errors that only surface at render time — a missing partial, a bad filter — are located by walking back to the calling tag in the template body, which is why the line and column are still exact. When one broken template affects hundreds of pages, it is logged a single time with the first page that hit it, so the output stays readable.

## A broken theme now fails the build

`fanstatic build` exits with a non-zero status code when template errors were found, so a broken theme can no longer
pass unnoticed in CI or in a deploy script.

```sh
# Still exits with 0 and reports every error
fanstatic build --continue-on-error
```

While `fanstatic serve` is running, template errors are additionally overlaid on the generated page in your browser, with the message and the offending tag in place of the broken output.

## Nested static folders are copied

`static/` folders were copied flat: every file landed directly in the root of the output, so `static/css/site.css` was published as `/site.css` and could silently overwrite a file of the same name from another folder. Site and theme static folders are now copied recursively, keeping their structure:

```
static/                        →   public/
├── robots.txt                       ├── robots.txt
└── css/                             └── css/
    └── site.css                          └── site.css
```

## An honest build report

The `Parse` and `Generate Pages` rows of the build report were reading the same counter, and that counter counted index files plus content sources — not Markdown files, and not pages. `Parse` now equals the number of Markdown files read, and `Generate Pages` the number of pages actually created, including the section, taxonomy, and term pages that Fanstatic generates for you:

```
Step                 Quantity        Duration
─────────────────────────────────────────────
Parse                83              18 ms
Generate Pages       181             39 ms
```

## Configurable taxonomies

Tags keep their existing behavior, and categories are enabled by default. Sites can now configure custom taxonomies, with term pages and metadata available to templates. Migrate tag links to `page.Taxonomies.tags` and build tag clouds from `site.Taxonomies.tags`, which exposes each term's URL and page count. The existing `page.Tags` and `page.TagsReference` properties remain available during migration. See the [taxonomy guide](/docs/content/taxonomy) for configuration and examples.

## Faster builds

Large sites build up to 23% faster, themes get cached sorted views such as `site.RegularPagesByDate`, and
`fanstatic build --template-metrics` shows which template is slow. Benchmarks on the MASS4 sites, charts, and a theme
migration guide are in [Faster Builds, Flatter Curves](/performance-initiative/).
